# Judge Treasury wallet lifecycle audit

Local code audit; no live wallet, database, or chain write was performed. The existing uncommitted recovery work was present before this audit and remains in place. The historical request `jr-07259520-7b7e-46d7-929c-df4ed67b8155` was not modified or independently investigated against production.

## Confirmed from code

- near-connect 0.12.0 supplies `signAndSendTransaction` returning an outcome by its declared API, but declares no callback URL in that method. Runtime errors or missing results remain possible. The app checks only `outcome.transaction.hash`; a missing result is UNKNOWN. There is no redirect callback ingestion or durable browser handoff marker. A returned hash can be entered manually and is not proof of success.
- Wallet eligibility was additionally limited to three named providers, with Nightly highlighted. The app requires Testnet, NEP-413 message signing and sign-in without an added key; the transaction path separately checks sign-and-send. The manifest describes capabilities, not proven interoperability. WalletConnect providers without configured project ID are filtered by the connector itself.
- The explicit verify action obtains a one-use browser-bound challenge, signs a message, and checks the connected account before and after verification. Sessions are server checked; refresh invalidates mismatched identities. The connector uses its first returned account; multi-account selection needs real-wallet verification.
- The server verifies session, contract code hash and finalized preflight, then commits the normalized action in a Postgres claim function. An owner/contract advisory transaction lock plus a unique business key serialize claims across serverless instances and tabs, assuming the reviewed migrations are actually installed. A client timeout can hide a committed claim; no process-local lock can substitute for the database. The app refreshes saved intents and leaves unresolved claims locked.
- `AWAITING_SIGNATURE`, `SUBMITTED` and `UNKNOWN` block funding for that owner and contract. The interface also displays Funding unavailable while `busy` is true. Thus the label immediately after Nightly confirmation can be an expected lock or in-progress state; it does not mean transaction failure. Without the original transaction and server evidence, the precise cause of the reported incident is unconfirmed.
- The wallet call occurs after asynchronous server operations. Browser transient activation can expire, plausibly causing a popup to be blocked. A timeout, navigation, rejected popup or lost response does not prove non-broadcast. There is no automatic unlock or rebroadcast. A failed claim response can itself conceal a committed claim.
- Reconciliation requires a valid original hash, finalized matching signer, receiver, method, gas, deposit and arguments; it then checks matching contract state and, for transfers, callback and recipient receipt evidence. RPC delays or conflicting evidence remain UNKNOWN. The existing local recovery changes conservatively keep even a failed candidate UNKNOWN because another broadcast may exist.
- The contract rejects reuse of a global request ID and payment ID, and binds later operations to the owner and request state. UUID request IDs reduce collisions but a fresh request ID creates a new payable operation: contract uniqueness is not cross-request idempotency. Duplicate create calls with the same ID fail rather than return an idempotent success; gas can still be spent. The owner/contract database lock is therefore essential and cannot protect activity outside this application or if the database is lost or bypassed.
- Postgres uses compare-and-swap transitions. Each Vercel instance can create its own max-one connection pool; aggregate connections and timeouts depend on instance count and Neon configuration. RPC preflight and session/database operations can exceed client/server deadlines. No production deployment settings or live concurrency were verified.

## Smallest viable path for reliable recovery

Keep the existing locks. Investigate a connector and each wallet's documented return/redirect mechanism that can durably associate a callback or original signed transaction hash with the already-claimed intent, including restart and cross-device recovery; validate candidates server-side using the existing strict reconciliation. A hashless broadcast cannot safely be ruled out from elapsed time or absent indexer history. A separate, explicitly authorized operator recovery process may be needed where no provable hash exists. Test browser activation and popup behavior with real wallets before claiming compatibility.

A contract revision is not necessary merely to enforce uniqueness of one request ID, but a stronger protocol would require a separately reviewed contract design binding a stable owner-scoped operation key to its immutable payload and recording outcomes, with defined duplicate-deposit behavior. It would not by itself recover a missing transaction hash or prove a rejected/never-submitted operation. No contract change or deployment is included here.
