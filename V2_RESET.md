# V2 reset and V1 inventory

V2 uses the `agentledger_v2` PostgreSQL schema and V2-specific cookies, business keys, request IDs and recovery storage. It does not copy rows from `public`. The old public payment-intent API and historical evidence endpoints return 410. Existing V1 rows, including UNKNOWN, remain untouched and cannot participate in V2 claims. V2 UNKNOWN operations still lock V2 claims to prevent duplicate payments.

The repository's V1 migrations identify `public.payment_intents`, `public.wallet_challenges`, and `public.wallet_sessions` as legacy tables; payment records are in `public.payment_intents`. Related functions and indexes also exist in `public`. Actual Neon contents, other tables and dependencies have not been inspected. `db/cleanup/v1_inventory_and_cleanup.sql` provides read-only inventory queries and a commented, scoped deletion proposal. UNKNOWN and pending records may be needed to recover real transactions. Review and back up data, identify affected deployments and dependencies, and obtain separate authorization before any destructive operation. Do not run this file as an automated migration.

`db/migrations/202611130001_v2_namespace.sql` creates a fresh empty V2 schema; it has not been applied. The app defaults to the deployed Testnet V2 contract ID and requires an explicit `V2_TREASURY_WASM_SHA256`; it also requires `V2_PAYMENTS_ENABLED=true` with `PAYMENTS_ENABLED=false` for signing. The contract must be a new, separate Testnet account using the independent V2 artifact, including paginated `get_payments_by_owner`; verify its deployment, code hash, behavior, empty initial state and migration permissions before enabling. The V2 Testnet contract was subsequently deployed and verified; see [deployment evidence](V2_TESTNET_DEPLOYMENT_EVIDENCE.md). The UI reads finalized contract requests as history; local intent records provide operational recovery and receipt verification, not authoritative payment status. The contract does not enumerate transaction hashes, so final receipt verification still requires the original hash. History is paginated and the overview summarizes the first page.

The V2 Testnet deployment is recorded in the deployment evidence. No database migration, destructive cleanup, account deletion or production configuration change was performed.

Before any separately authorized migration, verify the intended database and role, take a recoverable backup, and review the SQL in an isolated environment. The migration revokes PUBLIC access to the V2 schema, tables and functions. If the application and migration use different roles, the application role needs explicitly reviewed schema USAGE and the required table and function privileges; do not assume the migration grants them. The migration is not idempotent. Validate atomic claims, recovery, authentication, and V1 isolation on an authorized nonproduction database before scheduling rollout. Do not run the legacy `npm run db:migrate` command for V2.
